# План защиты (5 минут)

**1. Запуск (1 мин)**
- `cp .env.example .env && docker compose up --build`
- показать в логах: миграции, seed_demo, gunicorn запустился

**2. UI (1.5 мин)**
- регистрация нового пользователя -> сразу попадает в «Мои задачи»
- вход под alice: видны только её задачи, создать задачу, сменить статус на In Progress, комментарий
- открыть в адресной строке чужую задачу `/tasks/3/` (задача bob) -> 404
- `/projects/new/` под alice -> 403
- войти под manager: видны все задачи, кнопка «Новый проект», назначение задачи на bob

**3. API и код (1.5 мин)**
- `tracker/models.py`: `visible_for()` и право `view_all_tasks`
- `tracker/views.py`: `VisibleTasksMixin`, `PermissionRequiredMixin`
- `/api/` Browsable API: список задач, POST задачи, `/api/tasks/3/` под alice -> 404
- получить токен через `/api/auth/token/`

**4. DevOps и тесты (1 мин)**
- `docker compose exec web python manage.py test`
- `tracker/tests/test_security.py` - тесты на IDOR
- зелёный CI во вкладке Actions, `Dockerfile`, `docker-compose.yml`, `ci.yml`

## Возможные вопросы
- **Почему 404, а не 403 на чужую задачу?** 403 подтверждает, что задача с таким id есть, 404 ничего не выдаёт.
- **Где проверка прав?** В queryset (`visible_for`), а не в шаблоне, поэтому её нельзя обойти прямым запросом или через API.
- **Как появляется роль менеджера?** Группа «Менеджер» с правами создаётся data-миграцией, пользователя добавляют в группу через админку.
- **Зачем `select_related`?** Чтобы список задач не делал отдельный запрос на проект и исполнителя для каждой строки (N+1).
